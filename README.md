# 园林绿化养护管理平台

面向城市园林绿化植物的栽植养护、修剪造型、病虫害防治、灌溉施肥与绿地巡查的一体化绿化管理后台。

这是一个前后端分离的管理平台：前端 Vue 3 + Vite + TypeScript，后端 FastAPI（Python）。
两边各自独立启动，前端 dev server 已关掉自动打开页面，启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/              统一请求封装
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false）
├── backend/                  FastAPI（Python） 后端
│   ├── app/routers/          每个业务模块一组接口
│   ├── app/services/         业务规则与状态流转
│   └── app/store.py          内存数据仓库与示例数据
├── .gitignore
└── docker-compose.yml
```

## 启动

### 后端

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
./run.sh
```

健康检查：`curl http://127.0.0.1:8000/api/health`

### 前端

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，
需要自己访问。`/api` 由 vite 代理到后端 `http://127.0.0.1:8000`。

## 约定

- 每个模块的前端页面在 `frontend/src/views/<模块>/index.vue`，后端接口在
  `backend/app/routers/<模块>.py`，业务规则在 `backend/app/services/<模块>.py`。
- 列表接口统一返回 `{ items, total, page, size }`，动作接口统一返回 `{ ok, message }`。
- 状态流转只允许在 `app/services` 里改，路由层不做业务判断。

## 花卉造景：按区域与花期定位、按换花规矩排优先级

花卉造景在统一约定上多了一层“读数管线”，列表、详情、导出、运营概览共用同一份口径：

1. **去重**：同一造景编号重复登记时只保留「登记时间」最新的一版，旧版计入合并明细；
2. **缺字段过滤**：景观面积或花卉品种缺失（含面积不是正数）的记录先过滤，并逐条返回原因；
3. **花期阶段**：按「花期起/花期止」与当前日期判定蕾花期、初花期、盛花期、末花期、凋谢期；
4. **优先级**：按当前换花规矩（每阶段周期天数）推算下次换花日、剩余天数与优先级，列表从紧到松排列。

相关接口：

- `GET /api/flower`：`region/phase/priority/keyword` 筛选 + `page/size` 分页，响应多带
  `summary`（登记总条数、重复合并、缺字段过滤、在册片数、筛选片数、本页片数及明细）；
- `GET /api/flower/meta`：区域、花期阶段、优先级等筛选项；
- `GET/PUT /api/flower/rules`：读取/调整换花规矩，保存后全部在册造景按新规矩重算并返回变动对照；
- `GET /api/flower/{id}`：单幅明细（被合并或过滤的旧版会标注 `已归档`）；
- `POST /api/flower/{id}/actions`：`安排换花`，重置上次换花日后自动重排。

前端要点：筛选条件与页码同步在 URL（翻页/前进后退都锁定条件）；列表页由 `KeepAlive`
缓存，点进 `/flower/:id` 再返回会停在刚才的滚动位置；`stores/flower.ts` 对相同条件做
请求去重与结果缓存，运营概览页的“花卉换花快查”与列表页取到的是同一份数据，规矩更新后
缓存整体失效、两边同时按新口径重算。
